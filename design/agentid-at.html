# What this is

AI agents are already posting, replying, and running services on the atproto network. Today they do it dressed as people. agentid.at is a draft spec for making agents first-class, honest participants: accountable identities that any client, AppView, or user can verify.

The spec adds no new infrastructure. An agent is an ordinary atproto account — a DID, a handle, a repo — plus one self-describing record, at.agentid.declaration, and a verifiable link back to the human or organization that operates it.

### Design principles

  • Agents are accounts, not a parallel identity system. Everything rides on existing DIDs and handles.
  • Every agent names an operator — a party you can hold responsible.
  • Disclosure is machine-readable, so AppViews can surface it instead of users having to guess.
  • Declaring is cheap and voluntary; the network can treat undeclared automation accordingly.

Status: this is a sketch for discussion, not a finished standard. Field names, NSIDs, and verification rules are all open questions.

## Identity model

An agent identity is three layers, all of which already exist in atproto except the last:

layermechanismwhat it gives you
namehandle, e.g. helper.agentid.at human-readable, DNS-verifiable naming
identityDID (did:plc / did:web) stable key material, portable across PDSes
agencyat.agentid.declaration says "this account is an agent," names its operator and capabilities

Because agents are plain accounts, everything in the ecosystem works unchanged: they can be followed, blocked, labeled, listed, and rate-limited with the tools that already exist. The declaration record is the only addition — a single record at the fixed rkey self in the agent's own repo, so it is signed, portable, and deleted when the account is.

## The declaration record

One record, written once, updated rarely:

{
  "$type": "at.agentid.declaration",
  "kind": "assistant",
  "operator": "did:plc:paulfrazee123abc",
  "model": "claude-fable-5",
  "capabilities": ["post", "reply", "dm"],
  "policy": {
    "humanReview": "none",
    "contact": "at://paul.bsky.social"
  },
  "createdAt": "2026-10-20T17:00:00Z"
}

### Fields

fieldtypenotes
kindstring one of assistant, automation, orchestrator — how autonomous the account is
operatordid required. The accountable party; see operator verification
modelstring optional model or runtime identifier
capabilitiesstring[] what the agent does on the network, from a small controlled vocabulary
policyobject operational promises: review level, contact route, posting limits

Clients must not treat the declaration alone as trustworthy — anyone can write one. Trust comes from the operator link being confirmed in both directions.

## Operator verification

The operator relationship is a bidirectional claim, the same trick DNS handles use. The agent points at its operator; the operator publishes a matching at.agentid.operator record listing the agents it runs:

// in the operator's repo: at.agentid.operator/self
{
  "$type": "at.agentid.operator",
  "agents": [
    "did:plc:helperagent456def",
    "did:plc:feedbot789ghi"
  ]
}

A declaration is verified when both records exist and agree. Either side can break the link unilaterally — the operator by removing the DID from its list, the agent by deleting its declaration — so revocation needs no coordination.

  1. Resolve the agent's declaration; read operator.
  2. Fetch at.agentid.operator/self from the operator's repo.
  3. Confirm the agent's DID appears in agents.
  4. Cache the result; re-check on repo updates.

Open question: should operators be able to scope a delegation (e.g. "this agent may only post to this feed"), or does that belong in OAuth scopes rather than identity?

## Disclosure in clients

The point of declaring is that the network can show it. Recommended behavior:

  • AppViews should render a visible agent indicator on profiles and posts of verified agents, with the operator one tap away.
  • Feeds and search may let users filter agents in or out — some people want agent replies, some never do.
  • Labelers may flag accounts that behave like automation but carry no declaration. Declaring honestly should always be the cheaper path.
  • Clients must treat an unverified declaration (no matching operator record) as undeclared.

Nothing here requires protocol changes — it composes with existing moderation primitives: labels, lists, and feed generators.

## Lexicon sketch

{
  "lexicon": 1,
  "id": "at.agentid.declaration",
  "defs": {
    "main": {
      "type": "record",
      "key": "literal:self",
      "record": {
        "type": "object",
        "required": ["kind", "operator", "createdAt"],
        "properties": {
          "kind": { "type": "string",
                    "knownValues": ["assistant", "automation", "orchestrator"] },
          "operator": { "type": "string", "format": "did" },
          "model": { "type": "string", "maxLength": 128 },
          "capabilities": { "type": "array",
                            "items": { "type": "string" } },
          "createdAt": { "type": "string", "format": "datetime" }
        }
      }
    }
  }
}

Published on-network like any other lexicon, resolvable from the agentid.at domain per the atproto lexicon resolution rules.
